M4 is Complete for the Roadmap v3 Structured Content / Structured Document Foundation scope. Roadmap v3 redefined the former Smart Reading OS M4 into the Structured Content / Structured Document Foundation. This record governs the detailed M4 delivery boundary and current M4 status, but it does not itself authorize release, production readiness, commercial readiness, M5 implementation, Reader cutover, migration/backfill execution, or legacy deletion/deprecation. Completion evidence is recorded in [M4 Completion Review](../reviews/m4-completion-review.md), and the downstream input boundary is recorded in [M4 → M5 Handoff Package](../handoffs/m4-to-m5-handoff.md).

## 1. Status

M4 is Complete for the Roadmap v3 M4 scope as reconciled on 2026-07-24. The formal completion evidence concluded that all 17 exit criteria are satisfied or satisfied with nonblocking limitations, with no blocking findings, and that M4 is ready for milestone status reconciliation. Nonblocking and deferred findings remain governed by the completion review and M4→M5 handoff; M4 completion does not start M5, authorize Reader cutover, authorize migration/backfill execution, or claim production/commercial readiness.

## 2. Milestone goal

Establish the smallest coherent, application-independent Structured Content / Structured Document foundation that converts validated Structured Processing Result (SPR) into selected or accepted application content, preserves provenance and recovery evidence, and supports derived Reader projections without making provider output, SPR, or Reader serialization canonical.

M4 creates the application-independent content boundary after SPR and before Reader, Smart Reading Intelligence, Smart Archive, and downstream application consumers.

## 3. Historical redefinition

Roadmap v2 and the former current M4 combined inherited Structured Content work with Reader, Speed Reading, Notes, Flashcards, Mind Map, and broader Smart Reading scope. Roadmap v3 decomposed that overloaded milestone prospectively:

| Historical scope | Roadmap v3 destination | M4 relationship |
|---|---|---|
| Structured Content, Structured Document, selected/current lifecycle, evidence/assets, projection boundary, ProcessingRun decision | M4 | Foundational post-SPR work completed in M4. |
| Reader API/product, general reading, basic Speed Reading, navigation, image/table presentation, Recovery Presentation, lexical search, optional Notes/highlights | M5 | M4 prepares the content/projection boundary; Reader product behavior starts after that boundary. |
| Summaries, citation-backed Q&A, Flashcards, Mind Map, AI Tutor, RAG, semantic search | M6 | M4 prepares evidence, anchors, and provenance; selected intelligence is downstream. |
| Smart Archive, collections/folders, archive metadata/lifecycle, cross-document retrieval, evidence-backed knowledge surfaces, archive workflows | M7 | M4 prepares shared content foundations; archive product scope remains downstream. |

M4 is the completed Roadmap v3 foundation milestone. No M3.5 was introduced. Former scope was redistributed and preserved as historical continuity; it is not described here as failed, cancelled, abandoned, completed, obsolete, or erased.

## 4. Starting point / historical planning baseline

Historical planning baseline: The statements below describe the state when M4 was redefined on 2026-07-20. They are retained as planning history and are superseded for current status by the [M4 Completion Review](../reviews/m4-completion-review.md), the [M4 → M5 Handoff Package](../handoffs/m4-to-m5-handoff.md), and the completion reconciliation in this record.

Current completed state: M4 implemented durable Structured Content candidate persistence, explicit selected/current content lifecycle, deterministic Structured Document assembly, and durable ProcessingRun persistence. Reader remains on the legacy compatibility path because Reader adapter/cutover work is deferred to M5; M4 did not authorize Reader cutover, migration/backfill execution, or legacy deletion/deprecation.

M4 started from completed and substantially established upstream foundations:

- **M1 inputs:** Document aggregate foundation, SourceFile/source evidence, storage adapter, source retention, database/Alembic foundation, and current compatibility entities.
- **M2 inputs:** provider boundary, retained Raw Processing Result, source/provider provenance, storage references, and deterministic retained payload evidence.
- **M3 inputs:** SPR v1, provider-independent normalization, validation, deterministic serialization where applicable, page and document recovery semantics, diagnostics/warnings, topology and evidence links, fixtures/conformance evidence, and provider isolation.

Current implementation evidence indicates that Document and SourceFile foundations exist; Raw Processing Result retention exists; SPR runtime, validation, normalization, recovery, diagnostics, and evidence links exist; and SPR is provider-independent and noncanonical. M3 did not complete durable Structured Content. Durable Structured Content / SCV or accepted snapshot is not yet implemented, canonical selection lifecycle is not yet implemented, Structured Document assembly is not yet implemented, current Reader still relies on legacy/compatibility paths, ProcessingRun persistence is not yet established as the final durable model, durable Observation rows are not yet required by accepted Roadmap v3, and Smart Reading Intelligence and Smart Archive remain downstream.

## 5. Architecture boundary

```text
Source Evidence
→ Storage
→ Processing Provider
→ Raw Processing Result
→ Structured Processing Result
→ Structured Content / Structured Document
→ projection
→ Reader / API / applications
```

M4 owns the frontier from SPR to Structured Content / Structured Document and the projection boundary. Raw Processing Result is retained evidence. SPR is normalized, provider-independent processing output, but it is noncanonical. Structured Content / Structured Document is the durable or accepted application content boundary. Projection is derived and noncanonical. Reader product work begins in M5.

## 6. Required M4 scope

### A. Minimal Structured Content model

M4 must define the smallest application-independent representation needed for document-level identity, ordered content nodes, page/section relationships, text content, heading/hierarchy where available, asset references, evidence anchors, warnings/recovery state, and source/provenance traceability. It must not silently choose final table/class names or model every future archive, AI, annotation, or learning concept.

### B. Minimal content lifecycle

M4 must decide between, or define the minimum viable combination of, Structured Content Version (SCV), accepted Structured Content snapshot, selected candidate content, or another explicitly named version/acceptance model. Candidate processing output must be distinguishable from accepted/selected application content; accepted state must be explicit; rebuild/retry must not silently overwrite evidence; current content must be identifiable; and future revision/migration must remain possible. This plan does not choose full SCV by itself.

### C. Canonical/selected-content policy

M4 must define what canonical or selected means at this stage, who or what selects content, minimal automatic/manual selection rules, behavior for partial/degraded documents, the relationship between retained evidence and accepted content, and replacement/rebuild behavior. A decision record or ADR may be required. The algorithm is not defined here.

### D. SPR-to-content assembly

M4 must establish deterministic transformation from valid SPR into candidate Structured Content while preserving, where available, document/page ordering, block/node ordering, text, hierarchy, assets, geometry/evidence references, diagnostics, recovery facts, and provider/normalizer provenance. Provider-specific payload semantics must not leak past SPR.

### E. Structured Document assembly

M4 must define an application-independent assembled document view sufficient for document reading order, pages, headings/sections, ordered nodes, assets, evidence references, recovery state, and future projections. Reader UI behavior is not defined here.

### F. Evidence and asset anchors

M4 must establish testable anchor requirements sufficient for source traceability, page/node linkage, image/table references, recovery explanation, future M5 Notes/highlights, future M6 citations, and future M7 cross-document retrieval. Exact schema is deferred.

### G. Provenance

M4 must preserve traceability across this chain:

```text
Document
→ SourceFile
→ Raw Processing Result
→ normalization/processing identity
→ SPR
→ candidate/accepted content
→ projection
```

Minimum provenance fields must be defined conceptually without persisting provider secrets.

### H. Recovery propagation

M4 must carry M3 recovery facts into content/projection-ready form, addressing successful pages, partial pages/documents, no-usable-semantic-content pages, warnings/diagnostics, content absence versus processing failure, and asset-only or degraded cases where supported. User-facing rendering belongs to M5.

### I. Projection boundary

M4 must define the architectural boundary through which Reader-compatible content is derived. Projection must be generated from Structured Content / Structured Document, must not define canonical content, must be regenerable, must allow Reader Content Stream v2 compatibility, must allow future richer projections, and must prevent provider JSON and raw SPR from becoming durable Reader truth. Exact endpoint/API shape is deferred to M5 unless needed for boundary testing.

### J. Legacy compatibility and migration policy

M4 must decide how to treat existing ContentBlock, MineruResult, PdfPage, BookImage, and current Reader route/service behavior. Possible treatments include compatibility adapter, migration source, transitional read path, deprecation path, or replacement after M4/M5. A clear rule is required, but destructive migration must not be required before evidence and compatibility tests exist.

### K. ProcessingRun persistence decision

M4 must explicitly decide whether a minimal durable ProcessingRun is necessary for content-generation provenance, status visibility, retry/rebuild identity, Raw Result/SPR/content relationships, failure diagnostics, and future reliable async processing. Roadmap v3 leans toward a minimal durable ProcessingRun if live/reliable processing requires it, but the exact model is not pre-decided.

### L. Observation persistence decision

Runtime SPR observations exist. Durable Observation rows are not automatically required by accepted Roadmap v3. Persistence should be added only if evidence, citation, query, lifecycle, or audit requirements justify it, and the decision must be documented before M4 completion.

### M. Schema migration and compatibility discipline

M4 must require reviewed, migration-safe schema changes where applicable, compatibility with existing development/test data expectations, explicit handling of destructive assumptions, deterministic migration tests or equivalent validation, and documented rollback/forward-migration limitations. Exact Alembic revisions are not designed in this plan.

### N. Deterministic tests

M4 must require tests for SPR-to-content assembly, ordering, hierarchy, evidence anchors, assets, partial/degraded recovery, accepted/current content selection, projection generation, legacy compatibility/migration rules, invalid input/failure behavior, and deterministic serialization or stable comparison where appropriate.

## 7. Explicit non-goals

M4 explicitly excludes full Reader UI/product, full Speed Reading experience, durable Notes/highlights product, Flashcards, Mind Map, AI Tutor, RAG, semantic search, chapter-summary product, citation-backed Q&A product, full Translation, full TTS, Smart Archive, collections/folders, cross-document retrieval, final user/tenant product model, final auth provider, final AI provider, final vector database, final deployment target, general external pilot, commercial release, enterprise hardening, and a complete universal content ontology.

A minimal compatibility projection may exist only under the temporary Reader bridge policy in this plan.

## 12. Design decision reconciliation

The formal completion review reconciles the original open M4 design-decision rows. Selected/current content lifecycle, minimum content-node shape, evidence/asset anchors, ProcessingRun persistence, Observation non-persistence, projection boundary, legacy compatibility policy, partial/degraded acceptance behavior, asset/reference approach, current-content selection, and schema migration discipline are resolved or dispositioned for M4 completion. DEC-019 remains open but nonblocking for M4 and required before actual migration/backfill execution. DEC-020 remains explicitly deferred to M5 / production readiness and is nonblocking for M4.

## 13. Validation strategy

M4 validation should include contract/unit tests, fixture-based assembly tests, deterministic comparison tests, migration tests where applicable, integration tests for Raw Result/SPR/content relationships, compatibility tests for current Reader stream/routes, partial/degraded recovery tests, provenance/evidence-anchor tests, invalid-input/failure tests, no-secret-leak checks, link/document consistency review, and controlled live-provider evidence only where justified.

Live-provider smoke alone does not complete M4. Existing M3 provider smoke is upstream evidence, not M4 completion evidence. M4 tests and implementation evidence are recorded in the completion review. Downstream product, release, and M5 implementation work remain future work requiring separate authorization.

## 14. Production minimum

M4 requires only the production discipline necessary to protect the content boundary: migration safety, deterministic behavior, explicit failure states, provenance, cleanup rules for generated/transitional artifacts, no secret leakage, compatibility/migration plan, documented limitations, basic diagnostic logging, and reliable status linkage if ProcessingRun is required.

M4 does not require the full external pilot or commercial gate. That downstream gate remains separate and includes auth, ownership, secure deployment, quotas, observability, backup, retention/privacy, and security review before external/commercial claims.

## 15. M4-to-M5 handoff

M5 receives the explicit [M4 → M5 Handoff Package](../handoffs/m4-to-m5-handoff.md), including a stable Structured Content / Structured Document boundary; explicit current/accepted content identity; projection boundary; Reader-compatible projection or adapter strategy; page/section/node navigation foundations; asset/image/table references; recovery facts suitable for presentation; provenance/evidence anchors; legacy compatibility/migration rules; deterministic fixtures/tests; documented limitations; and processing status/provenance linkage if required.

M5 must not need provider-specific JSON, Raw Result parsing, direct SPR interpretation as durable product content, or legacy MineruResult/ContentBlock as canonical truth.

## 16. Risks and mitigations

| Risk | Impact | Mitigation | Completion Gate |
|---|---|---|---|
| M4 overdesign | Delays M5 and bloats foundation. | Keep smallest coherent application-independent model. | Content model decision and M5 handoff review. |
| SCV overengineering | Lifecycle becomes heavier than needed. | Compare SCV, accepted snapshot, selected candidate, and hybrid options. | Lifecycle decision before persistence work. |
| Content model too weak | Reader/intelligence/archive cannot rely on it. | Validate against M5/M6/M7 anchor and projection needs. | Ordering, anchor, recovery, projection tests. |
| Evidence anchors too weak for M6/M7 | Future citations/retrieval lose traceability. | Define testable anchor quality without final schemas. | Anchor tests and provenance review. |
| Temporary Reader bridge becoming canonical | Compatibility path replaces durable content model. | Label noncanonical, isolate, test, and document removal/migration condition. | Projection boundary and compatibility review. |
| Legacy migration complexity | Data loss or broken Reader behavior. | Require adapter/migration/deprecation rule and tests before destructive changes. | Migration/compatibility evidence. |
| ProcessingRun deferred too long | Status/provenance/retry identity remains unreliable. | Decide minimal durable run when live/reliable processing requires it. | Recorded decision before M4 exit. |
| Durable Observation overbuild | Persistence expands beyond Roadmap v3 need. | Persist only if justified by evidence, citation, query, lifecycle, or audit needs. | Observation decision before M4 exit. |
| Canonicalization ambiguity | Consumers cannot know current content truth. | Define selected/current meaning and replacement behavior. | Lifecycle tests. |
| Partial/degraded content mishandling | Users or downstream systems misread failures as content. | Propagate recovery facts and distinguish absence from failure. | Partial/degraded tests. |
| Schema migration risk | Development/test data or future migration path breaks. | Review migration-safe changes and limitations. | Migration validation. |
| Provider-specific leakage | Provider JSON semantics become application truth. | Enforce SPR boundary and provenance-only references. | Provider isolation tests. |
| Projection coupled to one Reader format | Future projections are constrained. | Keep projection derived and noncanonical. | Projection regeneration tests. |
| M5 blocked by excessive foundation scope | Reader MVP waits for nonessential platform ambitions. | Defer archive/AI/complete ontology concerns. | M4-to-M5 handoff review. |
| Production concerns ignored | Content boundary becomes unsafe or untraceable. | Include minimum migration, failure, provenance, cleanup, logging, and no-secret requirements. | Production minimum review. |
| Implementation work mistaken as authorized by milestone plan | Unreviewed code/schema/API changes occur. | State this plan withholds implementation and release authorization. | Separate reviewed implementation tasks required. |
