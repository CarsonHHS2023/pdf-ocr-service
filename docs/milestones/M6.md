M6 is Planned. M6 begins only after the required M4 Structured Content / Structured Document foundations and M5 Reader MVP foundations are stable enough to support intelligence without redefining canonical content or Reader behavior. M6 adds a selected subset of evidence-backed Smart Reading intelligence; the candidate list is prioritized but not fully mandatory. This plan does not authorize implementation, provider selection, external pilot, release, production claims, or commercial-readiness claims. Final selected features require later reviewed M6 scope decisions and separately authorized implementation decisions.

## 1. Status

M6 is the Planned Smart Reading Intelligence milestone in Roadmap v3. It is downstream of M4 and M5 and upstream of M7 Smart Archive. Planned means this milestone has a scoped planning boundary and future completion criteria; it does not mean implementation has begun.

M6 may only move beyond Planned after completion evidence demonstrates the selected M6 feature set and all required shared foundations. All completion criteria in this plan are Required / Not yet demonstrated.

## 2. Milestone goal

Add the smallest selected set of trustworthy Smart Reading intelligence capabilities over stable Structured Content and Reader foundations, ensuring that generated claims are evidence-backed, provenance-recorded, cost-bounded, privacy-aware, and clearly distinguishable from original document content.

M6 is not a mandate to implement every possible AI, learning, tutoring, retrieval, or generated-content feature.

## 3. Roadmap role

Roadmap v3 decomposes the former overloaded Smart Reading OS and Smart Archive scope into delivery stages:

- M4 provides the Structured Content / Structured Document foundation.
- M5 provides the Reader MVP over that foundation.
- M6 provides selected evidence-backed Smart Reading intelligence over M4 and M5 foundations.
- M7 provides Smart Archive as a downstream peer application over shared foundations.

M6 governs selected reading-intelligence capabilities, semantic search placement, retrieval/index planning boundaries, evidence and citation requirements, generated-content provenance, cost/privacy/security constraints, and handoff conditions for later M7 work. It does not update the roadmap, milestone index, architecture documents, Contracts, ADRs, product strategy, implementation code, migrations, tests, CI, deployment, or release status.

## 4. M4/M5 dependency and starting point

M6 depends on M4 providing:

- stable Structured Content / Structured Document identity;
- accepted/current content lifecycle;
- source, page, node, and asset evidence anchors;
- provenance chain;
- recovery state;
- deterministic content fixtures;
- projection boundary.

M6 depends on M5 providing:

- stable Reader projection and consumption behavior;
- navigation/location identity;
- lexical search behavior;
- supported document-type declarations;
- Reader fixtures;
- recovery presentation;
- ownership/security context where user-specific data exists;
- distinction between original content and generated content surfaces.

M6 must not treat any of the following as canonical knowledge truth:

- provider JSON;
- Raw Processing Result;
- Structured Processing Result (SPR);
- Reader serialization;
- legacy Reader tables;
- generated AI output.

Repository evidence inspected for this plan shows strong processing, storage, Raw Processing Result, SPR, fixture, CI, and Reader-contract context, but this milestone plan does not claim embeddings, semantic search, RAG, summaries, Q&A, Flashcards, Mind Map, or AI Tutor are already implemented.

## 5. Intelligence architecture boundary

M6 uses this derived-intelligence boundary:

```text
Source Evidence
→ Raw Processing Result
→ Structured Processing Result
→ Structured Content / Structured Document
→ Reader foundations
→ retrieval/evidence selection
→ generated intelligence
→ intelligence presentation
```

Original content remains canonical selected document content after the approved M4 lifecycle. Generated intelligence is derived content. Generated output must not overwrite source content, accepted Structured Content, Structured Document identity, or Reader presentation source. Every selected feature must preserve evidence and provenance where required. Semantic search and retrieval indexes are derived infrastructure, linked to content versions and rebuildable. M7 may consume shared foundations, but it remains a peer application and must not treat M6 generated artifacts as canonical archive truth.

## 6. Candidate-priority model

The accepted planning-priority order is:

1. Evidence-backed chapter summaries
2. Citation-backed document Q&A
3. Flashcards
4. Mind Map
5. Broader AI Tutor

This is an accepted planning-priority order. It does not require all five candidates. Final M6 completion scope must explicitly select the features included. M6 may complete with a smaller approved subset. Unselected candidates remain deferred. Semantic search is part of the M6 foundation or selected scope, but the exact implementation remains deferred.

## 7. Required shared M6 foundations

### A. Evidence and citation policy

M6 planning must define which generated claims require citations, acceptable evidence anchors, document/page/section/node/asset references, citation rendering expectations, handling of missing or conflicting evidence, citation integrity validation, and the distinction between direct evidence and model inference. The final citation UI remains deferred.

### B. Generated-content provenance

M6 planning must require conceptual recording of source document/content version, selected evidence, feature type, model/provider identity, model version, prompt/template version, configuration, generation timestamp, retry/regeneration identity, and applicable safety/filter state. M6 must not store secrets or full sensitive prompts without explicit review.

### C. Retrieval and indexing boundary

M6 planning must address lexical versus semantic retrieval, semantic search in M6, embeddings/indexes as derived and rebuildable, index-to-content-version linkage, deletion/rebuild behavior, stale-index handling, privacy and tenant boundaries, and prohibition on provider payload indexing as canonical truth. M6 does not choose a final vector database.

### D. Original-versus-generated distinction

Original document content and generated intelligence must remain separately identifiable. Generated output must be labelled and cannot silently replace canonical content. User edits or accepted generated artifacts, if later supported, require an explicit lifecycle decision.

### E. Cost and quota controls

M6 planning must require bounded requests, provider quotas, feature-level cost visibility, retry limits, caching/regeneration policy, large-document cost strategy, and refusal or degradation when budget limits are reached. M6 does not set final pricing or billing.

### F. Privacy and security

M6 planning must require access control alignment, ownership/tenant boundaries, provider data-handling review, sensitive-content treatment, logging/redaction policy, no secret leakage, deletion/retention interaction, and user-data handling for Flashcards or Tutor history if selected.

### G. Safe-answer behavior

M6 planning must require safe no-answer behavior, insufficient-evidence responses, conflicting-evidence handling, partial-document awareness, recovery/degraded-state awareness, provider/model failure handling, hallucination-risk communication, no fabricated citations, and generated-content labelling.

### H. Evaluation framework

M6 planning must require measurable evaluation for selected features, including evidence faithfulness, citation correctness, answerability/no-answer behavior, completeness where appropriate, deterministic or bounded variation expectations, regression fixtures, provider failure behavior, cost/latency observations, and privacy/security checks. M6 does not require one universal metric for all features.

## 8. Candidate feature definitions

### A. Evidence-backed chapter summaries

Planning scope may include chapter/section selection, evidence-linked summary statements, partial/degraded content handling, no-summary behavior where structure or evidence is insufficient, summary provenance, and distinction from original text.

### B. Citation-backed document Q&A

Planning scope may include document-scoped questions, retrieval over approved content, evidence citations, no-answer behavior, conflicting evidence, recovery-aware responses, provenance, and cost controls.

### C. Flashcards

Planning scope may include evidence-linked question/answer pairs, source anchors, regeneration/version behavior, user edits only if separately approved, and duplicate or low-confidence handling.

### D. Mind Map

Planning scope may include derivation from document hierarchy and evidence, nodes linked to source content, generated relationships clearly labelled, incomplete hierarchy handling, and no replacement of canonical document structure.

### E. Broader AI Tutor

Planning scope may include guided Q&A, explanations, comprehension prompts, evidence-backed feedback, conversation history only with explicit identity/privacy policy, and safe refusal and no-answer behavior.

All feature definitions are candidate definitions only. They do not make all features required.

- generated output replacing canonical document content;

## 13. Completion / exit criteria

All criteria are Required / Not yet demonstrated:

1. The selected M6 feature set is explicitly recorded.
2. Unselected candidates are not required for completion.
3. Selected features consume approved Structured Content / Reader foundations.
4. Generated outputs remain distinguishable from original content.
5. Evidence-required claims trace to approved anchors.
6. Citations do not fabricate or point to unrelated evidence.
7. Generated-content provenance records source/version, feature, model/provider, prompt/config version, and generation identity as approved.
8. Semantic indexes are linked to content versions and are rebuildable.
9. Stale/deleted content does not silently remain active in retrieval indexes.
10. Provider-specific payloads do not become canonical knowledge.
11. Cost, quotas, retries, and bounded large-document behavior are enforced.
12. Privacy/security and ownership boundaries are respected.
13. Safe no-answer behavior works when evidence is insufficient.
14. Conflicting or partial evidence degrades safely.
15. Recovery/degraded document state is reflected in selected features.
16. Provider/model failures produce deterministic safe product states.
17. Selected features have measurable evaluation criteria.
18. Tests cover evidence, citations, no-answer, partial evidence, provider failure, stale indexes, cost bounds, privacy boundaries, and selected feature behavior.
19. Generated intelligence is labelled in API/UI behavior.
20. M6 limitations and unselected scope are documented.
21. External pilot/commercial claims remain blocked unless the separate gate is satisfied.
22. M7 can consume shared content/evidence/retrieval foundations without making generated intelligence canonical archive truth.
23. Completion evidence is recorded before Milestone Status changes.

M6 may be Complete only for the explicitly selected feature set, and unselected candidates must remain out of completion requirements.

## 15. Evidence and citation policy

M6 evidence and citation principles are:

- cite evidence for factual generated claims where applicable;
- preserve document/content version identity;
- distinguish quoted, paraphrased, and inferred output where feasible;
- never fabricate citations;
- prefer no-answer to unsupported certainty;
- reduce confidence or scope when partial document recovery affects evidence;
- keep citations stable enough for supported content versions;
- defer exact citation UI/API details.

Evidence-required claims must trace to approved evidence anchors, such as document, page, section, node, or asset references. Missing, conflicting, stale, or degraded evidence must produce a safe answer state rather than unsupported authoritative output.

## 16. Generated-content provenance policy

Every selected generated feature requires conceptual provenance. Generated output must not silently be treated as source content. Provenance must address regeneration, retries, model upgrades, prompt changes, content-version changes, deletion, stale generations, and user-edited generations if later selected.

Conceptual provenance must include source document/content version, selected evidence, feature type, model/provider identity, model version, prompt/template version, configuration, generation timestamp, retry/regeneration identity, and applicable safety/filter state. Secrets and full sensitive prompts must not be stored without explicit review.

## 17. Cost, quota, privacy, and security policy

M6 must require bounded provider use, quotas and rate limits, cost observability, no infinite retries, large-document strategy, caching with version linkage, provider data-handling review, user/tenant access boundaries, deletion/retention behavior, no secret leakage, redacted logging, and explicit policy for persistent Tutor or Flashcard user state if selected.

Cost and privacy controls must degrade safely when budgets, quotas, provider availability, or access boundaries prevent generation. M6 does not decide final billing, subscription, provider, deployment, retention, or privacy policy.

## 18. Safe-answer and failure policy

M6 must define safe states for:

- no-answer;
- unsupported question;
- insufficient evidence;
- provider unavailable;
- index unavailable or stale;
- partial document;
- citation unavailable;
- cost/quota exceeded.

Safe user-facing messaging must explain limitation without fabricating fallback answers, citations, or confidence. Hallucination-risk communication and generated-content labelling are required for selected features.

## 19. External pilot/commercial gate

Before external users, external pilot claims, commercial claims, production claims, or release claims, Atlas requires at minimum:

- authentication;
- authorization;
- ownership/tenant boundaries;
- security review;
- reliable processing and intelligence status;
- retry/idempotency;
- secure storage/deployment;
- provider quotas and cost controls;
- observability;
- backup/restore;
- retention/deletion;
- privacy expectations;
- provider data-use review;
- incident/failure recovery;
- generated-content disclaimer and support expectations.

This gate is not Milestone Status. Passing it does not automatically authorize release. Internal controlled demos may precede it. M6 can complete internally without commercial release if milestone criteria are satisfied.

## 20. M6-to-M7 handoff

M7 may receive:

- stable Structured Content and provenance;
- evidence anchors;
- semantic retrieval/index foundations where selected;
- citation policy;
- generated-content provenance policy;
- safe-answer behavior;
- cost/security/privacy controls;
- selected cross-document-capable foundations only if explicitly approved;
- documented limitations.

M7 must not treat generated summaries, Q&A responses, Flashcards, Mind Maps, or Tutor responses as canonical archive content unless a later explicit lifecycle decision says so.

## 21. Risks and mitigations

| Risk | Impact | Mitigation | Completion Gate |
|---|---|---|---|
| M6 expands into every AI feature | Scope becomes unfinishable. | Require explicit selected-feature decision and defer unselected candidates. | Selected feature set recorded. |
| Uncited AI output is treated as truth | Users trust unsupported generated claims. | Require evidence/citation policy and generated labels. | Citation tests pass. |
| Fabricated citations | Evidence trust collapses. | Validate citations against approved anchors. | Citation integrity evidence. |
| Weak evidence anchors | Generated claims cannot be traced. | Depend on M4 anchors and reject unsupported claims. | Anchor validation evidence. |
| Stale embeddings/indexes | Retrieval surfaces deleted or outdated content. | Link indexes to content versions and rebuild/delete deterministically. | Stale-index tests pass. |
| Provider lock-in | Future model/provider changes become costly. | Version provider/model/config and keep provider choices deferred. | Provider abstraction review. |
| Model/prompt changes break reproducibility | Outputs cannot be audited. | Record model, prompt, template, and configuration versions. | Provenance tests pass. |
| Generated output becomes canonical | Source truth is corrupted. | Preserve original/generated separation and lifecycle gates. | Presentation/API review. |
| Cost blowout | Provider use becomes unsustainable. | Enforce quotas, bounded requests, caching, and large-document strategy. | Cost/quota tests pass. |
| Unbounded retries | Failures amplify cost and load. | Require retry limits and deterministic failure states. | Retry tests pass. |
| Sensitive data leaks to providers/logs | Privacy and security breach. | Provider-data review, redacted logging, no-secret checks. | Security/privacy checks pass. |
| No-answer behavior is bypassed | Unsupported certainty reaches users. | Require answerability tests and safe refusal policy. | No-answer tests pass. |
| Partial documents produce overconfident answers | Recovery gaps are hidden. | Make recovery/degraded state visible to features. | Partial/degraded tests pass. |
| Flashcards/Mind Map quality is unmeasured | Learning features become noisy. | Require selected-feature evaluation and low-confidence handling. | Feature evaluation evidence. |
| AI Tutor becomes open-domain chat | Scope and safety boundary fail. | Restrict to evidence-backed guided behavior if selected. | Tutor safety review. |
| Semantic search scope expands into archive scope | M6 consumes M7 archive workflows. | Keep Smart Archive and cross-document workflows out of M6 unless explicitly approved as shared foundation. | Scope review. |
| External demo is mistaken for commercial readiness | Release claims exceed evidence. | Apply external pilot/commercial gate separately. | Gate assessment. |
| Implementation work is mistaken as authorized | Planning document becomes accidental approval. | State implementation requires separate reviewed decisions and tasks. | Governance review. |
