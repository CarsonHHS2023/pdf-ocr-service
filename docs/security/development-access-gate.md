# Development Access Gate

This is a temporary shared-password access gate for the early development stage. It protects the application without introducing a user table, ownership model, registration flow, or refresh-token system.

It is intentionally separate from the future multi-user authentication and authorization design.

## Behavior

When `APP_ACCESS_ENABLED=true`, normal application routes require:

```http
Authorization: Bearer <access-token>
```

The following remain public by design:

- `/`
- `/api/v1/health`
- `/api/v1/health/config`
- `/api/access/login`
- `/docs`
- `/openapi.json`
- `/redoc`
- CORS `OPTIONS` preflight requests

Routes under `/internal/` are excluded from the shared app gate because they already use their own service/operator authentication.

The access token is an HS256 JWT with a default lifetime of 12 hours. The shared password is never stored in plaintext by this application; the configured value is a PBKDF2-SHA256 hash.

## Generate the two secrets

From a checkout containing this code:

```bash
python -m app.access_security hash-password
python -m app.access_security generate-token-secret
```

The first command prompts for the shared password twice and prints the value for `APP_ACCESS_PASSWORD_HASH`. The password must be at least 12 characters. The second command prints a random value for `APP_ACCESS_TOKEN_SECRET`.

Store both values as deployment secrets. Do not commit either value to the repository.

## Environment variables

- `APP_ACCESS_ENABLED`: `true` to enforce Bearer tokens. Defaults to disabled.
- `APP_ACCESS_PASSWORD_HASH`: PBKDF2-SHA256 hash generated by the helper above.
- `APP_ACCESS_TOKEN_SECRET`: random token-signing secret, at least 32 characters.
- `APP_ACCESS_TOKEN_TTL_SECONDS`: token lifetime. Defaults to `43200` (12 hours); allowed range is 300 through 86400 seconds.
- `APP_CORS_ORIGINS`: optional comma-separated explicit origins. If unset, the application allows the production GitHub Pages origin plus common localhost development origins.

## Safe rollout order

Use this order to avoid locking out the current production frontend:

1. Deploy the backend code with `APP_ACCESS_ENABLED=false`.
2. Add `APP_ACCESS_PASSWORD_HASH` and `APP_ACCESS_TOKEN_SECRET` as deployment secrets.
3. Verify `POST /api/access/login` returns a token for the chosen shared password.
4. Deploy the frontend login gate and its centralized authenticated fetch wrapper.
5. Verify the frontend can log in and use the application while the backend gate is still disabled.
6. Set `APP_ACCESS_ENABLED=true`.
7. Verify anonymous application requests now return `401`, valid Bearer requests succeed, health remains public, and existing `/internal/` authentication still works.

This staged activation deliberately keeps the code rollout separate from enforcement.

## CORS

CORS no longer uses a wildcard production origin. The default production origin is:

```text
https://carsonhhs2023.github.io
```

Additional origins should be supplied explicitly through `APP_CORS_ORIGINS` when needed.

CORS is not an authorization mechanism. Non-browser clients can ignore browser CORS rules, so the Bearer-token gate is the actual access control.

## Removing this gate later

When real user authentication is introduced, keep the frontend's centralized authenticated-fetch abstraction and replace this shared token source with the real user access token. Remove the shared password login endpoint and middleware only after all protected routes use the real authentication/authorization path.
